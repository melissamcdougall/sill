# PR #66 host-side integration assessment

Context pointer: `.scratch/mac-to-mac-in-sill-app/issues/01-assess-pr-66-host-integration.md` in the task checkout (the tracker file is maintained there, not copied into this research worktree).

## Finding

The richer viewer experience is a plausible fit for the existing Sill.app process and its host core, but PR #66's private virtual-display desk is not a safe drop-in change. The project's own current host already uses the private `CGVirtualDisplay` API for one selected window, behind a runtime-checked wrapper and with a real-window fallback. PR #66 turns that narrow, opt-in path into a multi-window display manager, captures menus and app UI through those displays, and changes window placement and lifecycle behavior. This is a major increase in the blast radius of a private API that the PR author reports can cause OS takeovers and leave a display unusable until WindowServer is killed or the Mac is restarted. Keep the per-window viewer UX as the target, but make the multi-display host implementation a separately gated validation decision; ship a public-API/real-window fallback and retain the existing single-window host stage unless multi-display trials meet a defined stability bar.

## What exists in Sill now

- Sill.app is already an AppKit menu-bar host. `Sources/SillMenuBar/AppDelegate.swift` starts one `AppModel`, whose host is the shared `SillHostCore`; the core is also used by the CLI. Its AppKit event loop is required by the existing virtual display implementation.
- The current host's `VirtualDisplay` uses Objective-C runtime name and selector lookup for private `CGVirtualDisplay`, validates method encodings, and reports failures. `VirtualStage` stages one selected host window and `StreamCoordinator` returns to capturing the real window when staging or capture fails. This seam supports an optional fallback without making the entire service unavailable. The code and the project brief explicitly identify the API as private/fragile.
- Mac viewer sources already live in `MacClient/`, but `Package.swift` builds them as the separate `SillClient` executable and `Scripts/make-client-app.sh` packages a distinct “Sill Viewer.app” (including a Dock helper). They share protocol and symlinked iOS session files, but the viewer has its own `App` lifecycle and its own app identity. Bringing the UI into Sill.app therefore involves composing the existing app delegate/menu host with the viewer's windows/session owners, not just moving files.

Primary source links: [current AppDelegate](https://github.com/Saffsanity/sill/blob/main/Sources/SillMenuBar/AppDelegate.swift), [VirtualDisplay](https://github.com/Saffsanity/sill/blob/main/Sources/SillHost/VirtualDisplay.swift), [VirtualStage](https://github.com/Saffsanity/sill/blob/main/Sources/SillHost/VirtualStage.swift), [StreamCoordinator](https://github.com/Saffsanity/sill/blob/main/Sources/SillHost/StreamCoordinator.swift), [Package.swift](https://github.com/Saffsanity/sill/blob/main/Package.swift), [viewer packaging script](https://github.com/Saffsanity/sill/blob/main/Scripts/make-client-app.sh), [project brief's risk and fallback](https://github.com/Saffsanity/sill/blob/main/docs/BRIEF.md).

## What PR #66 adds and what remains risky

PR #66's proposal gives each remote window a separate local window, with live side streams, remote menus and Dock proxies, input, clipboard, and remote desktop windows. Its host-side `DeskStages` allocates one private virtual display per remote window, reserves framebuffer memory, reuses display identities/slots, puts windows back when no viewer needs them, and monitors captured pictures. These lifecycle safeguards respond to real failures discovered while building the feature; they are not evidence that the platform behavior is stable.

In the PR description and discussion, the author reports virtual-desktop oddities, OS takeovers, and a soft-bricked display requiring WindowServer termination, logout, or reboot. The PR description also records ColorSync saturation after display churn, WindowServer watchdog restarts, and incorrect frames from a newly created display. The implementation consequently retains displays as spares, removes them only after the desk empties (and serially), limits framebuffer use, validates picture identity, and falls back to per-window capture in several failure cases. These mechanisms are complex and still leave known unconfirmed behaviors in the PR. They make the design an experimental host subsystem, not a routine refactor.

The existing host implementation already has one-display risk, so adopting the wrapper does not introduce a new private-API category. The risk changes in scale: from one stage associated with the current selected device stream to several long-lived hidden displays, windows moved between displays, app activation/take-back behavior, and display churn across concurrent sessions. A private-API lookup guard only detects a missing/changed runtime interface; it cannot contain WindowServer/ColorSync defects or restore a wedged display service.

## Public API and distribution boundary

Apple documents ScreenCaptureKit's `SCShareableContent`, `SCWindow`, `SCDisplay`, content filters, and `SCStream` for capturing windows or displays. Apple also documents Accessibility's `AXUIElement` interface. Those public APIs cover capture and window inspection/control used around the virtual displays; they do not provide a documented public API to create the hidden virtual monitors themselves. Apple's App Review Guideline 2.5.1 says App Store apps may only use public APIs. The current Sill Mac host is distributed as an outside-the-Mac-App-Store app, but a future App Store distribution would be incompatible with relying on this private API absent a public replacement or Apple's authorization.

Sources: [Apple ScreenCaptureKit capture guide](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [Apple SCStream](https://developer.apple.com/documentation/screencapturekit/scstream), [Apple AXUIElement header documentation](https://developer.apple.com/documentation/applicationservices/axuielement_h), [Apple App Review Guidelines §2.5.1](https://developer.apple.com/app-store/review/guidelines/).

## Protocol and scope drift

The rich per-window UI is not wire-compatible with today's protocol as implemented. PR #66 adds window side streams, per-window background input, desktop identity, and host take-back messages, as well as optional clipboard-image negotiation; its PR description enumerates kinds 29–42. It also includes separate audio and file-transfer features (kinds 33–38 in the PR's protocol summary). The experience can exclude audio and file transfer, but multiple simultaneously live windows and desktop windows still need additive protocol messages and host/client coordination. The PR's thread records that the existing kind 32 clipboard had to be reconciled with the already-landed clipboard shape, and its author proposed aligning audio with another PR. Thus “retain today's wire protocol” and “deliver the full PR #66 per-window experience” cannot both be literal requirements. Ticket 02 should define the minimum additive, capability-negotiated message set while explicitly excluding audio/file-transfer messages; old iPhone/iPad clients should continue to ignore unknown host messages and receive the current single stream.

Sources: [PR #66 protocol summary and feature list](https://github.com/Saffsanity/sill/pull/66), [maintainer's protocol drift note](https://github.com/Saffsanity/sill/pull/66#issuecomment-6195666555), [PR's clipboard compatibility update](https://github.com/Saffsanity/sill/pull/66#issuecomment-6197678450).

## Recommended boundary for the next decision

Integrate the viewer's menu action and separate session windows into the existing Sill.app composition, sharing its signed application identity and host process, while keeping host and viewer session state independent so either can run concurrently. Treat the PR's `DeskStages`/multi-display host change as an optional experimental path behind a capability/configuration gate. Before making it the default, validate on supported macOS versions with two Macs: display add/remove and sleep/wake, multiple windows over long sessions, app takeover/recovery, ScreenCaptureKit output identity, permission states, full-screen transitions, memory pressure, and clean quit/relaunch. Record a way back to the current real-window capture for every window and a global disable switch if the window server or displays misbehave. If those tests do not establish a safe operating envelope, retain the rich viewer presentation but initially use the public ScreenCaptureKit window capture path with its known occlusion/repaint limitation, or defer per-window presentation rather than shipping a host path that can wedge the desktop.

This boundary preserves current Sill host architecture and avoids coupling to PR #66's audio, file transfer, and Dock-proxy work. The host-side virtual-display decision remains distinct from the viewer UI integration; resolve it only after a dedicated real-hardware stability gate.
